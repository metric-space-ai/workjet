# CTOX Desktop App

## Register

product

## Users

CTOX is for developers and business operators who coordinate several coding
harnesses, LLM providers, worker profiles, computers, and closed CTOX Business
OS instances from one desktop workspace. They repeatedly switch between Code
threads and Business OS instances and need local and remote resources to feel
equally direct.

## Product Purpose

CTOX Desktop App is one coherent Electron client with two equal modes: Code and
Business OS. Code is the T3-derived coding workspace with native Workjet
orchestration. Business OS manages and opens authorized CTOX instances. The
modes share skills, tools, provider infrastructure, and explicit workflows,
while their runtime authorities and data stores remain separate.

Success means the user can independently choose a harness, LLM route/model,
worker profile, and local or remote computer; see delegated workers as normal
threads; manage ctox.dev, local, SSH, and Tailscale instances; and switch modes
without layout shift, delayed chrome, duplicated concepts, or hidden state.

## Brand Personality

Quiet, exact, and operational. CTOX should feel as immediate and trustworthy as
the best native developer tools: dense without clutter, restrained without
being empty, and confident without decorative product theater.

## Anti-references

- A broken overlay or two unrelated applications placed inside one window.
- Generic admin dashboards made from oversized cards, full-width setup buttons,
  repeated helper copy, or modal-first workflows.
- Renamed T3 screens that expose none of the native Workjet behavior.
- Settings that mix Code and Business OS ownership or collapse harness,
  provider route, model, and computer into one coupled selector.
- Loading states that pop, shift, reflow, or make local and remote resources feel
  fundamentally different.

## Design Principles

1. Equal modes, shared shell: Code and Business OS use the same spatial grammar
   and interaction quality without pretending they share one runtime authority.
2. Put control where work happens: instance, worker, provider, and computer
   actions live beside the objects they affect.
3. Independent choices stay independent: harness, LLM route/model, computer,
   capabilities, and worker prompt are explicit composable fields.
4. Stable before complete: reserve geometry immediately, render cached state
   first, and reconcile in place without layout jumps.
5. Capability, not product: Greppy, Web Stack, skills, and tools are shared
   facilities and never substitutes for Workjet orchestration itself.

## Accessibility & Inclusion

Preserve full keyboard navigation, visible focus, reduced-motion preferences,
screen-reader names and state, semantic status that does not rely on color, and
German-length labels without wrapping critical titlebar controls. Both dark and
light themes must retain the same information architecture and affordances.
