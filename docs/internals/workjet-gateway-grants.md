# Scoped provider gateway catalog

The existing `workjet.providerGateway.catalog` remains the environment-local, host-wide settings catalog. CTOX consumers use the additive `workjet.providerGateway.scopedCatalog` method with a target containing the selected CTOX `connectionId` and `instanceId` plus the execution `computerId`. The server checks the immutable connection-to-instance binding and that the computer exists in its Workjet configuration before returning a result. An unknown target fails with `target-unavailable`.

The scoped catalog starts empty. An orchestration-operate caller uses `workjet.providerGateway.setGrant` with `granted: true` to allow one gateway account for one target, or `granted: false` to revoke it. Grants live in a private `provider-gateway-grants.json` file beside the gateway configuration and survive server restarts. Removing a gateway account revokes its grants before deleting that account. A different computer or CTOX instance never inherits a grant. Read-only callers can inspect a scoped catalog but cannot change grants.

Every scoped account carries a logical credential reference `(environmentId, accountId)`, a provider reference `(environmentId, provider)`, and model references `(environmentId, provider, modelId)`. These identities are stable across Workjet process restarts on the same environment. Responses omit OAuth tokens, API keys, secret-store names, management credentials, and even the four-character credential suffix from the host-wide settings catalog. The grant file contains only target and account IDs. It is metadata, not credential transfer or a remote gateway proxy; a CTOX consumer must enforce the same target and selected references when it authorizes worker execution.
